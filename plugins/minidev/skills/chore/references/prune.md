# Pruning tests

Removes the tests that don't earn their place, across the whole project unless the user names a part of it. It's the one chore that removes existing tests, so it follows this procedure from start to finish instead of the chore's sections 2 and 3. The rules, the patterns, the protected tests and the sabotage are in the `build` skill's `references/test-value.md` (`../../build/references/test-value.md` from this file): read it first. The branch, checkpoints, review and merge follow `../../build/references/git-flow.md` and `../../build/references/review.md`.

1. **Branch.** Create `chore/prune-tests` (or `chore/prune-<part>`) as in `git-flow.md` (Start the branch), or resume it (Resume).
2. **Suite before.** Run the test suite and the build, and record the result and the number of tests. If they fail, stop and show the user: a prune on a red suite can't prove it removed no check.
3. **Map.** Handle skipped tests as `test-value.md` says. Tie each test to what it keeps: a rule of SPEC.md (or its Constraints), a regression, an outside contract. Find the protected tests (`Critical tests:` and `Regression tests:` blocks, or the fallback for older projects) and the `Redundant older tests:` blocks earlier changes left (`git log --grep "Redundant older tests:"`). There's no target number unless the user gives one, and even then a test that stays by the rules stays.
4. **List.** Show the user, in plain language and grouped by module, each candidate: the test, the pattern it fits, and the test that keeps its rule (or why it keeps nothing). Protected and "maybe protected" ones go in a separate group, named one by one. Also list the moves (misplaced tests) and, apart, the rules of SPEC.md no test checks. Wait for the user's OK; remove only what they approved.
5. **Remove** in batches, one module at a time, together with the production code only those tests kept alive (an unused export, wrapper or reset hook). After each batch, sabotage each rule that lost a test as `test-value.md` says (it starts with a checkpoint), run the module's tests and commit a `wip:` checkpoint.
6. **Suite after.** Run the whole test suite and the build: every test that stays and passed before must pass now.
7. **Record** each rule with no test as a Debt entry in BACKLOG.md, with the `document` skill. Don't write tests here: a prune only removes. SPEC.md and CHANGELOG.md don't change (a prune isn't news for users).
8. **Review** as in `review.md`, with the chore's description and the list of removals the user approved in the reviewer's prompt, and act on its report as that file says for `chore`.
9. **Verification commit** in the format of `git-flow.md` (The verification commit), with no Tester, `Critical tests:` or `Regression tests:` section. Under "what changed and why", give: tests before and after (count), test lines and production lines removed, counted apart, coverage per file before and after if the project measures it, the tests kept that looked useless and why, and what kept producing the useless tests. Each sabotage goes under Check of the tests.
10. **Suggest** a line for the project's CLAUDE.md that would stop the useless tests from coming back or, if the cycle itself produced them, a report to the plugin.
11. **Merge, test and push** as in `git-flow.md` (Merge and push), in the project's integration mode.
